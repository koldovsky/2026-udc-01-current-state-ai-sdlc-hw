# Task 2: Фіча через режими

## Фіча

**Очищення записаних даних + опціональний діапазон значень для графіка**

Дашборд мультиметра не мав можливості вручну очистити записані дані — лише автоматичне скидання при зміні режиму/одиниці. Також не було способу зафіксувати вікно перегляду графіка, що ускладнювало відстеження малих відхилень у сигналі.

---

## Acceptance Criteria

1. Кнопка **Clear data** — очищає дані графіка та записані вимірювання; активна лише якщо є дані
2. Опціональні поля **Min / Max** для осі Y графіка; порожні поля = автомасштабування
3. Якщо значення виходить за межі діапазону — цифровий дисплей показує реальне значення без змін
4. Графік **реагує** на вихід за межі: точки, що виходять за діапазон, відображаються як червоні крапки на межі осі
5. CSV-експорт містить реальні значення (не обрізані діапазоном)

---

## Plan Mode

Перед написанням коду сформулювали план у режимі планування Claude Code.

### Вибір інструменту планування

Спочатку спробували `/ultraplan` — режим, що запускає планування у хмарній сесії Claude Code на claude.ai. Виявилась суттєва незручність: хмарна сесія не має автоматичного доступу до файлів проєкту — їх потрібно вручну додавати до контексту. Це сповільнює роботу і підвищує ризик неповного аналізу коду.

Перейшли на **звичайний план-режим** (`/plan` у локальній сесії Claude Code) — він одразу бачить весь проєкт і не потребує ручного додавання файлів до контексту.

### Що аналізували

- `flushSession()` вже існував у `page.tsx` — ідеально підходить для кнопки Clear без дублювання логіки
- `ChartPoint` інтерфейс потребував нового поля `oor?: boolean`
- Chart.js підтримує масиви для `pointRadius` і `pointBackgroundColor` — це дозволяє виділяти OOR-точки червоним кольором на рівні датасету без додаткових плагінів
- Патерн `rangeMin`/`rangeMax` як рядки (порожній = без обмеження) — повторює вже існуючий патерн `threshold`

### Структура плану — три файли

| Файл | Зміни |
|------|-------|
| `RealtimeChart.tsx` | Розширити `ChartPoint`, додати `yMin`/`yMax` props, per-point OOR маркери |
| `page.tsx` | Стан `rangeMin`/`rangeMax`, обчислення OOR в `handleReadings`, нові props |
| `Controls.tsx` | Секція Chart Range (min/max inputs) + кнопка Clear data |

### Що скоригували після рев'ю плану

- Вирішили НЕ використовувати Chart.js annotation plugin (зайва залежність) — замість цього використали нативні масиви `pointRadius`/`pointBackgroundColor`
- `yScale.min = undefined` замість видалення ключа — Chart.js коректно повертається до автомасштабування при `undefined`
- Кнопка Clear використовує `canExport` як умову активності (той самий стан що й Save to CSV), не вводячи нового стану

## Agent Mode

Виконали план в агентному режимі по трьох файлах.

### `app/components/RealtimeChart.tsx`
- Додали `oor?: boolean` до `ChartPoint`
- Додали `yMin?: number`, `yMax?: number` до props компонента
- В ефекті оновлення даних: будуємо масиви `radii` та `colors` паралельно з `labels`/`values` в одному `for` циклі
- OOR точки: `pointRadius = 4`, `pointBackgroundColor = '#ef4444'` (червоний)
- Нормальні точки: `pointRadius = 0` (невидимі — лише лінія)
- Ліміти осі Y задаються динамічно: `yScale.min = yMin`, `yScale.max = yMax` (при `undefined` → автомасштабування)

### `app/app/page.tsx`
- Додали стан `rangeMin`, `rangeMax` (рядки, за патерном `threshold`)
- В `handleReadings` обчислюємо `oor` flag для кожної точки: порівнюємо `baseValue` з parsed `rMin`/`rMax`
- Реальне значення в `recordedRef` і цифровому дисплеї — незмінне
- `rangeMin`, `rangeMax` додані до deps масиву `handleReadings`
- Передаємо `onClear={flushSession}` до `Controls` (без нової логіки — reuse існуючого)
- `RealtimeChart` отримує `yMin`/`yMax` як `number | undefined`

### `app/components/Controls.tsx`
- Нова секція **Chart Range** між Recording і Export: два `<input type="number">` з placeholder "auto"
- Кнопка **Clear data** поруч із Save to CSV; disabled при `!canExport`
- Підказка: "Out-of-range points shown as red dots. Leave blank to auto-scale."

## Рев'ю дифу

Перевірили через `npm run lint` — нуль помилок. Логіка OOR не торкається:
- `recordedRef` (CSV завжди містить реальні значення)
- цифрового дисплея (`DigitalDisplay` не отримує `oor`)
- механізму тригера (порівнює `baseValue`, а не обрізане значення)

---

## Знайдений баг та виправлення

Після ручного тестування з реальним пристроєм виявлено баг у логіці OOR-маркерів.

### Опис проблеми

Тест-кейс: значення 9.7 кОм, діапазон Min: 7000 — Max: 9000. Всі точки мали бути червоними і відображатись на верхній межі осі. Натомість — жодних крапок взагалі, лише суцільна зелена лінія.

### Причина

Chart.js застосовує canvas clipping: будь-який елемент, чиє значення виходить за межі `yScale.min`/`yScale.max`, **не малюється взагалі** — він обрізається ще до рендерингу. Тому крапки з `pointRadius = 4` і кольором `#ef4444` фізично не потрапляли на полотно, хоча їх параметри були правильними.

### Виправлення

У `page.tsx`, при формуванні `ChartPoint`, додали затискання (`clamp`) відображуваного значення до межі діапазону:

```typescript
let chartV = baseValue;
if (oor && baseValue !== null) {
  if (rMax !== null && baseValue > rMax) chartV = rMax;
  else if (rMin !== null && baseValue < rMin) chartV = rMin;
}
const point: ChartPoint = { t: ..., v: chartV, oor };
```

Тепер OOR-точка відображається на межі осі як червона крапка, що наочно сигналізує про вихід за ліміт. `recordedRef` зберігає оригінальний `Reading` з реальним значенням — CSV-експорт не змінився.

### Урок

Поведінку Chart.js щодо canvas clipping не було враховано на етапі планування. Баг виявлено лише при тестуванні з реальним пристроєм. Це підкреслює важливість ручної перевірки з реальними даними навіть після успішного проходження лінтера.

---

## Висновок

Режим **Plan** допоміг уникнути зайвих залежностей (annotation plugin) і переконатися, що `flushSession` можна reuse без змін. Режим **Agent** виконав усі три файли без помилок.

**Порівняння режимів планування:**
- `/ultraplan` — запускається у хмарі, зручний редактор плану на claude.ai, але потребує ручного додавання файлів до контексту, що уповільнює роботу
- Локальний `/plan` — має повний автоматичний доступ до проєкту, підходить для задач де важливий повний контекст кодової бази

Ключове рішення — використати нативні масиви Chart.js замість плагіна — знайдено під час рев'ю плану. Баг з canvas clipping виявлено після імплементації і виправлено окремим цільовим патчем.
